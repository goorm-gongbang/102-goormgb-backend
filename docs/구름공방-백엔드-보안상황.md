## 1. 전체 방어 아키텍처

```
[외부 요청] 사용자 / 공격자 (curl, Selenium, Playwright)
       │
       ▼
[인프라 레이어] ← 클라우드팀 보완 영역
  Istio Sidecar / mTLS / Cloudflare WAF / 네트워크 정책
       │
       ▼
[게이트웨이 레이어] API-Gateway (:8080)
  ├─ JWT 인증 필터 (RSA256 서명 검증 + 블랙리스트 체크)
  ├─ 봇 UA 차단 필터 (curl/selenium/playwright 등)
  ├─ Rate Limiting (prod: IP당 로그인 10회/분, 일반 100회/분)
  ├─ CORS Origin 검증
  └─ X-User-Id / X-Session-Id 헤더 주입
       │
       ▼
[서비스 레이어]
  ├─ Auth-Guard: RSA JWT 발급 / RTR / 유저 차단 / Kafka 이벤트
  ├─ Queue: Redis 대기열 / Admission Token / Pre-Queue 검증
  ├─ Seat: Redisson 분산 락 / Admission Token 검증 / Hold 수량 제한
  └─ Order-Core: 주문 UUID / 소유권 통일 응답 / Kafka 차단 이벤트 소비
       │
       ▼

  ├─ PostgreSQL: AES-256-GCM 필드 암호화 (email, nickname, phone)
  ├─ Redis: 토큰 블랙리스트 / Refresh Token / 대기열 / 분�� 락 / Rate Limit
  └─ Kafka: user.blocked 이벤트 / 예약 확정 이메일 발송

       ◀◀ AI 방어 서버 연동 ▶▶

[AI 방어 서버] ← AI팀 보완 영역
  Istio에서 수집한 메트릭 분석 → 실시간/사후 봇 탐지
```

## 2. 인증 체계 상세

### 2.1 JWT 토큰 구조 (RSA256 비대칭키)

모든 JWT는 **RSA256 (RS256)**으로 서명합니다. Auth-Guard만 개인키를 보유하고, API-Gateway/Queue/Seat은 공개키로 검증만 수행합니다.

| 구분           | Access Token                                  | Refresh Token                       |
|--------------|-----------------------------------------------|-------------------------------------|
| **용도**       | API 요청 인증                                     | Access Token 재발급                    |
| **서명**       | RSA256 (개인키)                                  | RSA256 (개인키)                        |
| **만료**       | 15분 (local/staging 동일)                        | 3시간 (local), 환경변수로 조정 가능            |
| **전달 방식**    | Authorization: Bearer 헤더                      | HttpOnly + Secure + SameSite 쿠키     |
| **audience** | `playball-goormgb-api`                        | `playball-goormgb-auth-service`     |
| **issuer**   | `playball-goormgb-auth-service`               | `playball-goormgb-auth-service`     |
| **클레임**      | userId, authority, sid, jti, tokenType=ACCESS | userId, sid, jti, tokenType=REFRESH |
| **저장**       | 클라이언트 메모리                                     | Redis (`refresh_token:{jti}`)       |

### 환경별 키 관리

|              | local                                                                       | dev                       | staging / prod            |
|--------------|-----------------------------------------------------------------------------|---------------------------|---------------------------|
| **JWT 개인키**  | application-local.yaml에 하드코딩 (테스트용 2048bit RSA)                             | 환경변수 `${JWT_PRIVATE_KEY}` | 환경변수 `${JWT_PRIVATE_KEY}` |
| **JWT 공개키**  | application-local.yaml에 하드코딩                                                | 환경변수 `${JWT_PUBLIC_KEY}`  | 환경변수 `${JWT_PUBLIC_KEY}`  |
| **키 포맷**     | 개인키: PKCS#8 base64 DER / 공개키: X.509 base64 DER                              | 동일                        | 동일                        |
| **환경별 키 분리** | local, dev, staging, prod 모두 **서로 다른 RSA 키 쌍** 사용 - 한 환경의 키로 다른 환경 토큰 검증 불가 |                           |                           |

### 2.2 Refresh Token Rotation (RTR)

Refresh Token 재사용을 탐지하여 토큰 탈취에 대응합니다.

```
// 최초 로그인
Client -> POST /auth/kakao/login (또는 /dev/auth/login)
Server -> Access Token 발급 (15분)
       -> Refresh Token 발급 -> Redis 저장 (key: refresh_token:{jti})
       -> Refresh Token은 Set-Cookie (HttpOnly, Secure, SameSite)

// 토큰 갱신 (RTR)
Client -> POST /auth/tokens/refresh (Cookie에 Refresh Token 포함)
Server -> 1. Refresh Token 서명 검증 (RSA256 공개키)
       -> 2. Redis에서 jti로 조회
            +- 불일치 -> 탈취 의심 -> 401 REFRESH_TOKEN_MISMATCH
            +- 일치 -> 계속
       -> 3. 기존 Refresh Token Redis에서 삭제
       -> 4. 새 Access + Refresh Token 발급 (sid는 유지, jti만 변경)
       -> 5. 새 Refresh Token Redis 저장

// Redis에 저장되는 RefreshTokenInfo
Key: refresh_token:{jti}
Value: {
  userId, token, jti, sid,
  issuedAt, expiresAt,
  userAgent,   // 로그인 시 브라우저 정보
  ipAddress    // 로그인 시 클라이언트 IP (X-Forwarded-For)
}
TTL: Refresh Token 만료시간과 동일
```

### 2.3 Access Token 블랙리스트

```
// 로그아웃 시
Client -> POST /auth/logout (Authorization: Bearer {accessToken})
Auth-Guard -> Access Token에서 JTI 추출
           -> Redis에 저장: key=token_blacklist:{jti}, TTL=토큰 잔여 만료시간

// 이후 모든 API 요청
API-Gateway -> JwtAuthenticationFilter
            -> 토큰 서명 검증 후
            -> Redis token_blacklist:{jti} 존재 여부 확인 (Reactive)
            -> 존재하면 401 BLACKLISTED_TOKEN
```

## 3. 대기열 & Admission Token

### 3.1 대기열 구조 (Redis Sorted Set)

| Redis Key                          | 타입            | 설명                            |
|------------------------------------|---------------|-------------------------------|
| `queue:wait:{matchId}`             | Sorted Set    | WAITING 상태 유저 (score = 진입 시각) |
| `queue:ready:{matchId}:{userId}`   | String (JSON) | READY 상태 유저 + Admission Token |
| `queue:ready:index:{matchId}`      | Set           | READY 상태 userId 인덱스 (빠른 조회)   |
| `queue:expired:{matchId}:{userId}` | String "1"    | 만료된 대기열 마커 (TTL 300초)         |
| `queue:match`                      | Set           | 현재 활성 대기열이 있는 경기 ID 목록        |

### 3.2 Admission Token (RSA JWT)

대기열을 통과한 유저에게만 발급하는 **일회용 RSA 서명 JWT**입니다. 좌석 서비스(Seat)에 접근하려면 이 토큰이 필수입니다.

| 항목            | 값                                                                             |
|---------------|-------------------------------------------------------------------------------|
| **서명**        | RS256 (Queue 모듈 전용 RSA 키 쌍 - JWT와 별도)                                         |
| **TTL**       | 900초 (15분)                                                                    |
| **Ready TTL** | 60초 (local: 30초) - READY 상태 유지 시간                                             |
| **issuer**    | `queue-service`                                                               |
| **subject**   | userId (Long -> String)                                                       |
| **커스텀 클레임**   | `matchId` (Long) - 특정 경기에 바인딩 / `type` = `"ADMISSION"`                        |
| **jti**       | UUID - 일회용 식별자                                                                |
| **전달 방식**     | Set-Cookie (HttpOnly, Secure, SameSite=None)                                  |
| **키 관리**      | local: 하드코딩 / dev~prod: `${ADMISSION_PRIVATE_KEY}`, `${ADMISSION_PUBLIC_KEY}` |

```
// 대기열 -> 좌석 접근 전체 흐름
1. POST /seat/booking-options     -> 예매 옵션 저장 + Redis PreQueue 마커 설정
2. POST /queue/matches/{id}/enter -> Pre-Queue 검증 (booking-options 확인 + UA 차단)
                                  -> Redis Sorted Set 대기열 진입
3. GET  /queue/matches/{id}/status
     WAITING -> (스케줄러 500ms 주기로 승격)
     READY   -> Admission Token 발급 (Set-Cookie)
4. POST /seat/matches/{id}/hold   -> Admission Token 검증
                                     +- RSA 서명 검증
                                     +- matchId 일치 확인
                                     +- userId 일치 확인
                                     +- 만료시간 확인 (410 ADMISSION_TOKEN_EXPIRED)
                                     +- 통과 -> Redisson 분산 락으로 좌석 확보
```

> **Admission Token과 JWT의 키는 완전히 분리**되어 있습니다. Auth-Guard의 JWT RSA 키와 Queue의 Admission Token RSA 키는 별도의 키 쌍이므로, JWT로
> Admission Token을 위조하거나 그 반대도 불가합니다.
>

## 4. 데이터 암호화

### 4.1 AES-256-GCM 필드 레벨 암호화

개인정보가 포함된 DB 컬럼을 **AES-256-GCM**으로 암호화합니다. staging/prod 프로필에서만 활성화되며, local/dev에서는 NoOp (평문 저장)입니다.

| 항목          | 값                                                                    |
|-------------|----------------------------------------------------------------------|
| **알고리즘**    | AES/GCM/NoPadding                                                    |
| **키 크기**    | 256비트 (32바이트, base64 환경변수 `${DB_ENCRYPTION_KEY}`)                    |
| **IV**      | 12바이트 랜덤 생성 (NIST 권장, 매 암호화마다 새로 생성)                                 |
| **인증 태그**   | 128비트 (GCM 모드 무결성 보장)                                                |
| **저장 형식**   | Base64( IV(12B) + Ciphertext + Tag(16B) )                            |
| **활성 프로필**  | `@Profile({"staging", "prod"})` - `AesEncryptionProvider`            |
| **비활성 프로필** | `@Profile({"local", "dev", "test"})` - `NoOpEncryptionProvider` (평문) |
| **JPA 적용**  | `@Convert(converter = EncryptionConverter.class)`                    |
| **캐싱**      | ThreadLocal 캐시로 Hibernate dirty-check 시 재암호화 방지                      |

### 암호화 대상 엔티티 및 필드

| 엔티티             | 모듈          | 암호화 필드                                                            | 설명                              |
|-----------------|-------------|-------------------------------------------------------------------|---------------------------------|
| **User**        | common-core | `email`, `nickname`, `profileImageUrl`                            | 사용자 기본 개인정보                     |
| **UserSns**     | common-core | `providerUserId`                                                  | 카카오 계정 식별자 (+ SHA-256 해시 별도 저장) |
| **Order**       | Order-Core  | `ordererName`, `ordererEmail`, `ordererPhone`, `ordererBirthDate` | 주문자 개인정보                        |
| **Payment**     | Order-Core  | `accountNumber`, `accountHolder`                                  | 환불 계좌 정보                        |
| **CashReceipt** | Order-Core  | `number`                                                          | 현금영수증 번호 (전화번호 또는 사업자번호)        |
| **Inquiry**     | Order-Core  | `phoneNumber`                                                     | 문의자 연락처                         |

### 4.2 SHA-256 해싱

OAuth provider 사용자 식별자(카카오 계정 ID)는 `HashUtil.sha256()`으로 해시하여 별도 컬럼에 저장합니다. 원본은 AES 암호화하고, 조회용 해시를 인덱스로 사용합니다.

## 6. AI 방어 서버 연동

### 백엔드가 제공하는 API

| Endpoint                           | Method | 인증                      | 동작                                                         |
|------------------------------------|--------|-------------------------|------------------------------------------------------------|
| `/internal/users/{userId}/block`   | POST   | `X-Internal-Api-Key` 필수 | User.status → BLOCKED + Kafka → Order-Core 주문 UNDER_REVIEW |
| `/internal/users/{userId}/unblock` | POST   | `X-Internal-Api-Key` 필수 | User.status → ACTIVATE (차단 해제)                             |

### 차단 시 자동 처리

```
AI 방어 서버
  │  POST /internal/users/{userId}/block
  │  Header: X-Internal-Api-Key: {secret}
  ▼
Auth-Guard
  ├─ 1. User.status = BLOCKED (PostgreSQL)
  ├─ 2. 차단 유저 로그인 시도 → 403 USER_ALREADY_BLOCKED
  ├─ 3. TransactionSynchronization.afterCommit()
  └─ 4. Kafka publish → topic: user.blocked, payload: { userId, occurredAt }
         ▼
Order-Core (KafkaListener)
  └-> 해당 userId의 활성 주문 → status = UNDER_REVIEW
```

### 백엔드에서 수집하는 유저 메타데이터

| 데이터              | 저장 위치                         | 수집 시점                       |
|------------------|-------------------------------|-----------------------------|
| IP Address       | Redis (RefreshTokenInfo)      | 모든 로그인 (Kakao/Dev/LoadTest) |
| User-Agent       | Redis (RefreshTokenInfo)      | 모든 로그인                      |
| Session ID (sid) | JWT 클레임 + Redis               | 토큰 발급 시                     |
| 로그인 시각           | PostgreSQL (User.lastLoginAt) | 로그인 시                       |
