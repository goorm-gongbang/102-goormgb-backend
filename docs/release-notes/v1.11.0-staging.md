## 주요 변경 사항

부하테스트에서 확인된 DB 커넥션 풀(`db.t4g.small`, max_connections 270) 소진으로 인한 upstream 503 에러를 완화하기 위해, Seat/Queue/Order-Core 에 걸쳐 정적·준정적 조회를 Caffeine 로컬 캐시로 흡수하여 DB 호출량을 대폭 감소시켰습니다.

## 기획/클라우드팀 참고 사항

### 부하테스트 개선 목표

- **1000~1500 VU, P95 <1s 달성** — 현 인프라(`db.t4g.small`, max_connections 270) 기준 현실적 목표
- **3000 VU 이상, 5000 VU** — DB 인스턴스 업그레이드(`db.m6g.large`, max_connections ~900) 필요. 본 릴리즈 범위 밖

### DB 호출량 감소 기대치

| 서비스 | 캐싱 대상 | DB 쿼리 감소 (예상) |
|--------|---------|------------------|
| Seat | Match/Section/Block 조회 3종 | **요청당 3~5회 → 0~1회** (cold 시만) |
| Queue | Match 존재/상태 조회 | **요청당 1회 → 0회** (cold 시 제외) |
| Order-Core | 주문서 조회 Match | **요청당 1회 → 0회** |

### 관측 방법

각 서비스 `/actuator/metrics/cache.gets` 에서 hit/miss 비율 확인 가능 (recordStats 활성화)

```bash
curl .../seat/actuator/metrics/cache.gets?tag=cache:match-detail
curl .../seat/actuator/metrics/cache.gets?tag=cache:section-all
curl .../seat/actuator/metrics/cache.gets?tag=cache:blocks-by-section-ids
curl .../queue/actuator/metrics/cache.gets?tag=cache:match-for-queue
curl .../order/actuator/metrics/cache.gets?tag=cache:match-detail
```

### 정합성 고려 사항

- **Match/Stadium/Section/Block** 은 배포 단위로만 변경되는 준불변 데이터로 TTL 기반 eventual consistency 로 충분합니다.
- **Queue 서비스** 는 티켓팅 오픈 시점의 `saleStatus` 전환이 최대 1분 지연될 수 있습니다 (TTL 1m).
- **Order-Core `createOrder`** 는 영속성 컨텍스트 보존을 위해 캐시를 적용하지 않았습니다. 주문서 조회(`getOrderSheet`)에만 적용됩니다.

### 롤백 절차

문제 발생 시 각 서비스 `application.yaml` 의 `spring.cache.type: caffeine` 을 `none` 으로 변경하면 `@Cacheable` 이 모두 no-op 으로 처리되어 DB 직접 조회로 즉시 폴백됩니다.

## 알려진 이슈

- **5000 VU 부하에서 503 지속 발생 가능**: 본 릴리즈는 현 인프라 범위 내 최적화이며, 5000 VU 레벨은 DB 인스턴스 업그레이드가 선결되어야 합니다.
- **Phase 2 후보**: Auth-Guard `UserRepository` Redis 분산 캐싱, `/auth/me` 응답 Redis 캐싱, 추천 서비스 `OnboardingPreference` 캐싱 (별도 작업계획)
